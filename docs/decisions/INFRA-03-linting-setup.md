# INFRA-03: ESLint, OXLint and Prettier

## Status

Accepted for quality configuration. `lint` and `format` are implemented and working. `type-check` and `build` are deferred to issues `#4-#8`, where stores, contracts, and final imports will be implemented.

## Context

The project needs a formatting tool and a dual linting pipeline to maintain code consistency, detect errors, and enforce the rules defined in `docs/wiki/Programming-Rules.md` and `docs/wiki/Coding-Style-Guide.md`.

Issue #3 states that OXLint must run first and ESLint second, as well as including scripts for formatting, type checking, and building.

## Decisions

- Prettier is used with `semi: true`, `singleQuote: true`, `printWidth: 100`, `trailingComma: 'all'` and `tabWidth: 2`.
- OXLint is used as the primary linter via `npm run lint:oxlint`.
- ESLint 10 is used with flat configuration in `eslint.config.ts` as the secondary linter via `npm run lint:eslint`.
- `eslint-plugin-vue` is used for Vue 3 rules, along with Vue's recommended TypeScript config and `eslint-plugin-oxlint` to avoid duplicating rules already covered by OXLint.
- Browser globals used by the application are explicitly declared in ESLint.
- The cache generated by ESLint is excluded from version control via `frontend/.eslintcache` in `.gitignore`.
- `<script setup>` blocks in SFCs are declared with `lang="ts"`, adhering to the project's TypeScript architecture.
- `@ts-nocheck` is not accepted as a permanent solution because it hides errors and contradicts strict TypeScript and ESLint rules.

## Reasons

- OXLint provides fast validation for general rules, and ESLint retains specific rules for Vue and TypeScript.
- Running OXLint before ESLint respects the pipeline defined by the issue and prevents both tools from competing over the same rules.
- Flat config is the required format for ESLint 10.
- Keeping Prettier separate from linting maintains clear responsibilities: Prettier formats, and linters detect quality issues.
- Ignoring the cache prevents generated files from being included in commits and pull requests.

## Alternatives Considered

- Using only ESLint: rejected because the issue demands a dual pipeline with OXLint.
- Disabling `vue/block-lang` to keep JavaScript scripts: rejected because it contradicts the project rule of using `<script setup lang="ts">`.
- Adding `@ts-nocheck` to SFCs: rejected as a quality solution because it prevents TypeScript from reporting errors and triggers the `@typescript-eslint/ban-ts-comment` rule.
- Installing an additional dependency for browser globals: rejected because the required globals are few and can be explicitly declared in the local configuration.

## Implemented Scripts

| Script | Command | Responsibility |
|---|---|---|
| `lint` | `run-s "lint:*"` | Runs OXLint then ESLint |
| `lint:oxlint` | `oxlint . --fix` | Fast linting |
| `lint:eslint` | `eslint . --fix --cache` | Vue and TypeScript rules |
| `format` | `prettier --write --experimental-cli src/` | Source code formatting |
| `type-check` | `vue-tsc --build` | Type checking |
| `build` | `run-p type-check "build-only {@}" --` | Parallel type-check and build |

## Consequences

- `npm run lint` and `npm run format` are available for all developers from this infrastructure phase.
- SFCs do not use `@ts-nocheck`; type errors are not hidden just to force a green result.
- `npm run type-check` and `npm run build` remain pending because views still depend on `src/store` and pre-refactor imports.
- Issues `#4-#8` must complete Pinia, interfaces, DTOs, seeders, and stores; afterward, all validations must be executed again.
- The PR must explain this scope and should not present `type-check` or `build` as successfully passing in this phase.

## Validation

- `npm run lint`: correct.
- `npm run format`: correct.
- `npm run type-check`: pending due to contracts, stores, and imports from future issues.
- `npm run build`: pending due to the same `type-check` errors.
